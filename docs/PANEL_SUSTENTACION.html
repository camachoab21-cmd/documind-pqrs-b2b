Guion Estructurado de Sustentación (3 a 5 Minutos)

Estructura cronológica para presentar con seguridad ante el profesor y tus compañeros.

1. Introducción y Propósito del Sistema (40 seg)
"Buenas tardes, profesor. El objetivo de nuestro proyecto fue automatizar el proceso empresarial de recepción, enrutamiento, gestión y auditoría de Requerimientos Institucionales (PQRS) para un entorno B2B. Conectamos cuatro capas desacopladas: Portal Web reactivo, Orquestador n8n, Base de datos relacional PostgreSQL y Servidor SMTP de notificaciones."
2. Demostración de las 5 Fases de Automatización (90 seg)
"Cumplimos al 100% las 5 fases exigidas en la rúbrica:
• Entrada: Capturamos la solicitud con un identificador idempotente (UUID) para evitar duplicados.
• Procesamiento: n8n normaliza los textos y calcula matemáticamente la fecha y hora límite de atención (SLA) según hora legal de Colombia.
• Toma de Decisión: Un nodo condicional bifurca entre la Ruta Urgente (< 4 horas) para quejas y reclamos de alta prioridad, y la Ruta Estándar (24 a 48 horas) para peticiones ordinarias.
• Acción Automática: Se dispara un correo SMTP con el comprobante al solicitante y alertas al supervisor.
• Almacenamiento: Persistimos todo en tablas normalizadas de PostgreSQL con trazabilidad de auditoría inmutable."
3. Valores Agregados de Ingeniería de Software (50 seg)
"Para llevar el proyecto a un nivel de producción, incorporamos dos elementos clave:
1. Seguridad RBAC y Privacidad: El ciudadano solo accede a su caso con su clave criptográfica; el listado completo y la gestión requieren credenciales corporativas autenticadas.
2. Control de Concurrencia y Calidad CSAT: Manejamos bloqueo optimista por versión de caso y una encuesta de satisfacción de 1 a 5 estrellas al resolver el ticket."

Banco de Preguntas y Respuestas Técnicas

Respuestas sólidas y fundamentadas a las preguntas más frecuentes de los evaluadores.

¿Por qué utilizan un identificador UUID (request_id) en el formulario antes de enviar a n8n?
Respuesta técnica: Para garantizar el principio de idempotencia en sistemas distribuidos. Si el usuario experimenta intermitencia de red o presiona dos veces el botón, n8n y la base de datos verifican si ese request_id ya fue procesado y devuelven el mismo comprobante, evitando generar radicados duplicados.
¿Cómo aseguran que dos agentes no sobreescriban los datos del mismo caso al mismo tiempo?
Respuesta técnica: Implementamos Concurrencia Optimista. Cada registro en pqrs_solicitudes tiene una columna entera version. Cuando el agente abre el modal, lee la versión actual. Al guardar, el backend valida WHERE ticket_id = $1 AND version = $2. Si otro agente ya modificó el caso, la versión en base de datos habrá aumentado y el sistema rechazará la operación con HTTP 409 (Conflict).
¿Cómo calculan el SLA y por qué en horas corridas?
Respuesta técnica: El motor de n8n toma la marca de tiempo de radicación (fecha_radicacion) y, con base en la matriz de prioridad y tipología, suma algebraicamente el número de horas configuradas en la política empresarial, calculando sla_fecha_limite de forma explícita en la zona horaria America/Bogota (UTC-5) para garantizar validez jurídica e institucional.
¿Cómo protegen la privacidad de los datos personales de los clientes?
Respuesta técnica: Aplicamos el principio de mínimo privilegio mediante Roles (RBAC). El endpoint público de consulta exige tanto el número de radicado como un tracking_token de 128 bits entregado únicamente al solicitante. De esta forma, ningún tercero puede enumerar o escanear solicitudes ajenas.
